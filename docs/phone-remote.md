# Paired phone remote

Open **Device → Phone remote**, choose a private IPv4 interface and the strip to control, then select **Enable HTTPS remote**. The phone must be on the same reachable network. Loopback is offered for testing on this computer only. The app binds only the selected address, does not open router ports, and does not modify firewall rules. If your OS asks, allow the app only on the intended private network. Guest Wi-Fi/client isolation may prevent access.

Open the displayed HTTPS address on your phone. Each enabled session generates a self-signed certificate. Compare the browser's certificate SHA-256 fingerprint with the value in the desktop app before pairing. The app can display the public certificate PEM; no private key is exported or installed in a trust store. Some mobile browsers cannot inspect or accept self-signed IP certificates; use a browser that supports this flow. Real iOS/Android browser and private-network/firewall validation remains part of physical QA. Do not send a pairing code through an unverified certificate warning or expose this listener to the internet.

Enter a recognizable phone name and the desktop's six-digit code. A code is single use, expires after two minutes, and closes after five failed attempts. Create another code for each additional phone. Up to eight clients can be paired. The desktop lists names and recent activity; revoke one or all immediately. The remote has power, brightness, solid color and saved-profile controls. Capture profiles are shown unavailable and cannot be started remotely. Color changes select ordinary Solid mode, while brightness/color edits preserve the stopped state. Start and Stop remain explicit.

All credentials, certificate keys, listener settings and client approvals are session-only. App restart, disabling or re-enabling the remote revokes clients and changes the endpoint/certificate. Pairings also expire after 24 hours. Expiry uses both monotonic and wall time so OS sleep cannot extend codes or client credentials; a backwards wall-clock jump fails closed. After sleep or network loss the phone disables controls and offers Reconnect. While the desktop reports a lifecycle pause, the worker rejects remote mutations except Stop. If the network interface address changes, disable and enable with the new address. The selected controller stays fixed for the remote session, independently of the desktop's current editing selection.

## Security and protocol

- TLS 1.2/1.3 uses Rustls with the Ring provider; Rcgen creates the session certificate with the chosen IP SAN. No plain-HTTP command endpoint exists.
- A random 256-bit per-client token is returned only in a `Secure; HttpOnly; SameSite=Strict; Path=/` `__Host-` cookie. The server stores its SHA-256 digest and an atomic revocation guard. Client tokens and private keys are never logged, written to disk, placed in URLs, returned in phone status, or exposed to JavaScript. The short-lived pairing code is shown in the main desktop window and entered into the phone form; it is never persisted.
- Exact Host and HTTPS Origin, JSON content type, no duplicate headers, no chunked requests, 8 KiB headers and 32 KiB bodies. No CORS. Static assets have a restrictive CSP, no framing, and no external requests. One connection at a time, 10 requests/second with burst 20, a four-second absolute transport deadline including TLS, and a two-second HTTP read budget bound resource use. A hostile peer on the chosen network can still disrupt availability; this is a private LAN service.
- `/pair` accepts `{code,name}`. `/v1/command` uses the existing versioned control request envelope. Its allowlist is `status`, `profiles`, `power`, `brightness`, `color`, and `applyProfile`, with capture permission always false. Routine, file, arbitrary settings, shell, shutdown, capture and plugin-management commands are unavailable. No captured RGB, screenshots, audio, local paths, diagnostic details, or game payloads are exposed. Saved profile names and basic lighting state are intentionally visible to paired clients.
- Revocation reaches the worker before mutations, including commands queued before revocation. OS pause and capture checks also happen on that worker. Each controller retains its single USB writer. No state snapshot preflight can grant capture consent.

The shared local API and CLI also gain `color`: `dynamiclight color '#336699'`. This is an additive API v1 command and uses the existing local automation credential; the CLI does not reuse phone pairing cookies. Existing terminal install scripts and release naming remain unchanged.

## Validation

Native tests exercise one-use/expired/rate-limited pairing, client revocation, permitted command boundaries, private status filtering and a real TLS loopback server/client with certificate/IP validation. The isolated Windows smoke test verifies the actual desktop IPC/server, HTTPS Origin/cookie enforcement, revoked commands, a 390px phone page and brightness/color/Stop while USB and capture stay off. The fixture temporarily disables lock/display-off suppression only in its isolated test settings so it can exercise controls on a locked test host, then restores those settings. Browser desktop tests cover enabling, pairing renewal and revocation controls. These tests do not claim real phone, firewall, USB or OS lifecycle hardware validation.
