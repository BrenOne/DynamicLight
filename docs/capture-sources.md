# Window and region capture

In Screen or Blend, choose **Capture source**. Full display keeps the existing display selection. Rectangle captures a selected portion of that display; drag its outline or enter left/top/width/height percentages. The display diagram previews geometry without taking a screenshot. Once started, the regular LED preview shows sampled edge colors.

For a video playing inside a browser page, choose **Application window**, refresh the window list, and select the browser. Click **Take window preview**, then drag a rectangle around the video itself. **Apply source**, then **Start / Retry**. The lights sample the selected area's edges; including white page margins or toolbars can produce white LEDs even when the video is orange. Alternatively, enable **Select an area within this window** and enter percentages without taking a preview. Uncheck it to use the whole window, for example with fullscreen video.

The preview button explicitly captures one still image of the chosen window. It is downscaled in memory, displayed only in this dialog, and discarded on close or source change; it is never saved, exported, or sent to the network. Opening the dialog and refreshing window names do not take screenshots. Taking a preview does not start LED output or authorize ongoing capture. Windows uses the same capture backend for the preview and lighting.

Window capture follows the visible contents of the browser window, not a pinned tab or a detected video element. Switching tabs changes what is captured. A selected area keeps its relative position and size when the window resizes; take another preview and reselect the video if the page layout changes. Black-bar detection can trim dark letterboxing inside the selected area; it does not remove white browser UI.

Window selection lists available applications and titles locally. Choose **Refresh windows**, select the intended window, and Apply. Applying a new source stops capture; Start / Retry is required to capture it. Movement and resizing are followed. Minimization, closure, or a revoked source interrupts screen capture. Blend can continue with its available audio source. Restore/reselect the window and Retry; opt-in capture recovery retains its usual behavior.

Window IDs are bound to their process and the current DynamicLight session. Re-select a window after restarting DynamicLight. This prevents a saved window ID being silently reused for another application. Local profiles retain source bindings; exported scenes exclude window identities, titles, and region/display bindings.

Rectangle coordinates are normalized to the selected display, or to the selected window for a window area, and rounded out to physical pixel boundaries. The rectangle therefore retains its relative coverage at different scale factors. Display resolution/rearrangement still uses the existing source-change recovery policy. The selected physical display determines LED edge allocation; a window or rectangle changes sampling coordinates without reassigning LEDs to different physical edges.

## Platform behavior

- Windows window capture uses a retained [Windows Graphics Capture session](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow), requiring Windows 10 1903+. The free-threaded pool is polled without calling the target application's blocking PrintWindow implementation. The OS capture indicator remains enabled. Explicit handle/process/minimization checks prevent continued use of a closed window's last frame. Full display keeps Desktop Duplication and GDI fallback; rectangles use a bounded GDI thumbnail of the selected region.
- macOS uses the selected window or display-region capture API through xcap. Screen-recording permission is required. Validate behavior on physical Intel and Apple Silicon Macs before claiming platform parity.
- Linux supports X11 window/region capture. Wayland remains unsupported, avoiding the screenshot-to-disk/repeated-prompt fallback. Compositor-dependent occlusion behavior must be validated on the target desktop.

Protected video, DRM, secure desktops, permission restrictions, and unsupported GPU paths can yield black or unavailable frames. The application does not bypass these protections. Captured pixels are sampled locally; only RGB lighting colors reach USB. Window titles and source IDs are excluded from diagnostic exports and the automation status API.

Native validation includes rectangle rounding at multiple resolutions, padded RGBA/BGRA sampling, source-change consent revocation, and export privacy. An interactive Windows test queries the audio device before repeatedly starting/stopping capture of its own generated fixture window. It reproduces white margins around an orange video, verifies selected-area output and one-shot preview colors, checks live red-to-blue changes, grows and shrinks the window, then verifies capture terminates on closure. No USB or audio recording is used by that test. Each Windows lighting worker initializes the multithreaded Windows Runtime before audio discovery and retains it across capture sessions, preventing the audio library's default single-threaded COM initialization from blocking later window capture with `0x80010106`. A separate regression test checks that worker lifetime without opening capture or audio devices. Physical multi-DPI, protected video, macOS and Linux window behavior remain in the platform validation trackers.
